# LIMPI 유지보수·확장 정비 계획

최초 분석: 2026-10-10. 분석 대상: Kotlin 소스 70개, 약 10,598줄, 능력 42개, 퀘스트 4개 및 빌드·리소스 설정.

처음 요청은 검토와 Paper 26.3 전환이었다. 이후 사용자가 작업 브랜치 생성, **전체 정비 구현**, 문서 갱신, 커밋과 가능한 push를 승인했다. 현재 브랜치는 `refactor/maintenance-paper26.3`이며 main 병합은 금지한다. **실제 서버 시험은 전체 구현 이후로 미룬다.** 단위/저장소 시험과 빌드는 구현 중 계속 수행한다. 구체적인 변경과 다음 작업은 [구현 기록](IMPLEMENTATION_LOG.md)을 기준으로 이어간다.

## 1. 이 플러그인이 하는 일

- 경제: 플레이어 잔액, 송금, 수표 발행/사용, 운영자 잔액 조정, 상점 구매/판매, 주식 거래와 가격 변동, 유저 간 마켓.
- 능력: 능력 획득/선택/도감/대상 설정, 능력별 전투·이동·상호작용 효과, 능력 아이템과 상태값 관리.
- 뽑기: 티켓, 등급별 확률/천장, 픽업, 애니메이션, 에메랄드 기반 능력 상점.
- 퀘스트: 조건 달성 후 특정 능력을 해금하는 4개 퀘스트.
- 능력 등급 분포: COMMON 10, RARE 13, EPIC 7, LEGENDARY 7, MYTHIC 2, TROLL 3.

현재 흐름은 `LIMPI.onEnable()` → 파일/설정 초기화 → 이벤트·능력 등록 → 명령어 등록이다. 이벤트와 명령어가 GUI, 게임 규칙, YAML 읽기/쓰기까지 직접 수행한다. `FileManager`의 공유 설정, `AbilityManager` 재생성, 능력 객체 초기화 시 실행되는 작업에 의존한다. 이 결합 때문에 기능을 하나 추가해도 저장·메뉴·명령·수명 관리까지 여러 곳을 함께 수정해야 한다.

## 2. 상태와 우선순위

- `완료`: 구현과 기록에 적힌 검증이 끝남. 검증 범위를 넘어선 동작까지 보장한다는 뜻은 아님.
- `미해결`: 아직 구현이 남아 있는 문제. `부분 해결`은 구현된 범위와 남은 범위를 구현 기록에 구분한다.
- P0: 잔액/아이템 손실·중복, 거래 무결성, 플레이어 상태 훼손. 구조 개편에 앞서 보호해야 함.
- P1: 잘못된 기능 동작, 메인 스레드 I/O, 수명/취소 처리, 확장 시 바로 드러나는 결함.
- P2: 코드 구성, 운영/테스트/문서화, API 정리.

## 3. 문제 목록과 수정 방향

## 4. 목표 구조

처음부터 멀티 모듈·범용 프레임워크로 나누지 않고 단일 Gradle 프로젝트에서 기능별 경계를 먼저 세운다.

```text
limpi/
  LIMPI.kt                  # 생성·등록·시작·종료만 담당
  player/                   # PlayerProfile, 접속/이탈, 프로필 서비스
  economy/                  # Money, 원장, 송금, 수표, 아이템 전달
  market/                   # 매물과 구매 서비스
  stock/                    # 가격 정책, 보유 원가, 거래
  ability/                  # 정의/레지스트리, 세션, 대상·피해 정책, 개별 능력
  gacha/                    # 확률·천장 정책, 결과 확정, 연출
  quest/                    # 진행 이벤트, 조건, 완료/보상
  menu/                     # Holder, 메뉴 세션, 페이지, 액션
  platform/                 # Paper 이벤트/스케줄러/명령 연결
  storage/                  # repository, YAML 어댑터, DB, migration
  config/                   # 타입 있는 설정, 검증, 메시지
```

- **규칙 → 서비스 → 저장소/플랫폼**으로 의존한다. 이벤트/명령어는 입력 변환과 서비스 호출에 집중한다.
- 초기에는 YAML 저장 어댑터와 캐시로 결합을 줄인다. 그 다음 거래 무결성이 필요한 잔액/원장/매물/보상부터 SQLite로 옮긴다. 운영 설정은 YAML로 유지할 수 있다.
- 플레이어 데이터는 단일 프로필/저장 경로를 통해 읽고 쓴다. 여러 FileConfiguration 복사본으로 동일 플레이어를 갱신하지 않는다.
- `AbilityDefinition`은 안정적인 코드명, 등급, 원소, 획득 방식과 검증된 설정을 가진다. `AbilitySession`은 UUID별 런타임 상태/작업/엔티티를 가진다. activate/deactivate/death/quit/disable 처리를 정의한다.
- 레지스트리는 시작 시 한 번 만들고 ID로 조회한다. 새 능력은 구현과 등록 한 곳으로 추가한다. 현재 42개 규모에서는 reflection 자동 탐색이나 별도 DSL이 필수는 아니다.
- GUI는 슬롯 → action/안정적인 대상 ID 연결만 가진다. 금전·획득 규칙은 메뉴에 넣지 않는다.
- 뽑기/퀘스트의 보상 확정은 저장과 함께 처리하고, 시각 효과는 그 뒤에 실행한다.
- SQLite를 도입해도 DB와 인벤토리 동시 원자성은 생기지 않는다. pending delivery, 재시작 복구, 중복 방지 키를 반드시 함께 설계한다.

## 5. 실행 순서와 완료 조건

1. **현재 계약 고정**: 기능별 입력/결과, 기존 데이터 예시, 위 P0 재현 절차를 기록한다. Paper 26.3 빌드와 서버 없이 수행할 수 있는 시험을 기준선으로 삼는다. 실제 서버 확인은 사용자 지시에 따라 전체 수정 후 수행한다.
2. **타입·저장 경계**: Money/PlayerProfile/설정 검증, repository와 YAML 어댑터, 단일 캐시, 저장 오류 전달. 매 틱 YAML 읽기가 사라져야 한다.
3. **경제 무결성**: 송금/매물/수표/판매/지급 거래 ID와 원장, 원자 처리, pending delivery, 실패·재시작 복구. 큰 금액과 동시 구매에서 자산이 보존되어야 한다.
4. **능력 수명 관리**: 레지스트리 단일화, 세션/전환/정리, 슬롯 물품 보호, 속성 modifier, 전투/대상 정책. 교체·이탈·사망·disable 이후 잔여 효과가 없어야 한다.
5. **메뉴·명령·뽑기·퀘스트 분리**: 메뉴 공통 입력 처리, 안정 ID, 페이지, 명령 정의, GachaPolicy와 확정/연출 분리, 퀘스트 멱등 보상.
6. **42개 능력 점진 이전**: 단순 패시브 → 입력/쿨다운 → 반복 작업/엔티티 → 특수 피해/단발 능력 순서. 각 능력 동작을 확인한 뒤 기존 경로를 제거한다.
7. **데이터 이전·운영 준비**: schemaVersion, 백업/건식 검증/복구, CI, 운영자 가이드. 전체 재작성 파일을 한 번에 운영 서버에 덮어쓰지 않는다.

긴 구조 전환 중에도 P0 결함은 별도 작은 수정으로 먼저 막을 수 있다. 단, 바뀐 동작과 재현 시험을 기록하여 후속 리팩터링에서 되돌아가지 않도록 한다.

## 7. 호환성·이전 원칙

- 기존 능력 코드명, UUID, 아이템 종류와 사용자 설정 의미를 먼저 목록화한다. 이름을 바꾸려면 이전 매핑을 제공한다.
- YAML을 지우거나 초기화해서 새 구조로 전환하지 않는다. 원본 백업 → 건식 변환 → 레코드 수/잔액 합계/해금·퀘스트 비교 → 실제 전환 순서로 진행한다.
- 저장 실패는 성공 메시지로 숨기지 않는다. 운영자가 원인과 복구할 거래/플레이어를 찾을 수 있게 기록한다.
- Paper 업데이트와 전체 구조 개편을 같은 변경에 섞지 않는다. 이번 업데이트의 변경/검증은 별도 문서에 남긴다.
